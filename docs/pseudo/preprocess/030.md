# 030 전처리 스도코드 (자연어 상세 버전)

## 0) 목적
`docs/plans/preprocess.md`의 공통 전략을 그대로 따르며,  
`030.웹데이터 기반 한국어 말뭉치 데이터`를 공통 스키마(6컬럼)로 평탄화한 뒤  
`duckdb -> arrow -> lance` 순서로 통합 저장소(`data/korean_processed/`)에 적재한다.

030 데이터는 **전량 FT**로 처리한다.

---

## 1) 사용자요청확인 반영(확정값)
아래 항목은 구현 시 그대로 하드 규칙으로 반영한다.

1. 본문 concat 구분자  
    사용자요청확인: `named_entity[i].content[*].sentence`는 `" "`로 결합
2. 제목 다문장 결합 규칙  
    사용자요청확인: `named_entity[i].title[*].sentence`는 전체 문장을 `" "`로 결합
3. 극단적 장문 기사 처리  
    사용자요청확인: 전처리 단계에서 자르거나 분할하지 않고 1기사 1row 원문 유지
4. 품질 리포트 샘플 수  
    사용자요청확인: 제외 사유별 샘플 최대 20건 (`QUALITY_SAMPLE_PER_REASON = 20`)

공통 고정값:
- 토크나이저: `data/tokenizers/korean_bbpe_v1/tokenizer.json`
- 인덱스 생성 시점: 전체 데이터셋 적재 완료 후 1회
- manifest 버전: 정수 증가(`v0001`, `v0002`, ...)
- 품질 리포트: 전체 집계 + 제외 사유별 샘플

## 3) 공통 스키마 선언 절차
다음 순서로 단일 PyArrow schema를 선언한다.

1. 컬럼 순서를 고정한다.
- `data_type: string`
- `source: string`
- `split: string`
- `content: string (nullable)`
- `messages: list<struct<role:string, content:string>> (nullable)`
- `token_count: int32`

2. null 규칙을 고정한다.
- FT row에서 `content=null`, `messages!=null`
- PT row에서 `messages=null`, `content!=null`
- 030은 FT만 생성하므로 항상 `content=null`

3. 스키마 버전 메타를 로드한다.
- 이전 manifest가 있으면 `schema_version`, `token_count_version` 검증
- `token_count_version`은 `TOKENIZER_ID`와 일치하는지 검증
- 버전 불일치 시 즉시 중단하고 사용자 확인 요청

## 4) 전체 실행 오케스트레이션
`전처리_030_실행()` 절차는 아래와 같다.

1. 실행 시작 로그를 기록한다.
- run_id, 시작 시각, 입력 경로, 정책 요약
- 정책 요약에 `BODY_JOINER`, `TITLE_JOINER`, `TOKENIZER_ID`를 반드시 포함

2. 입력 파일 목록을 수집한다.
- train 파일 목록 정렬
- val 파일 목록 정렬
- 총 파일 수 기록

3. DuckDB 정규화 단계로 진입한다.
- 파일별 파싱 결과를 중간 row 스트림으로 생성
- 기사 단위 이상치 제외 정책 적용
- 표준 컬럼 6개로 relation 생성

4. Arrow 변환 단계로 진입한다.
- relation -> Arrow Table/RecordBatch
- 공통 schema 강제 캐스팅
- 캐스팅 실패 row는 오류로 집계하고 실행 중단 여부 판단

5. Lance chunk 적재 단계로 진입한다.
- chunk 버퍼를 열고 row를 순차 추가
- 바이트 추정/실측을 갱신
- 임계값을 넘으면 “방금 추가한 row까지 포함”하고 chunk 마감
- 다음 row부터 새 chunk 시작

6. 매니페스트와 품질 리포트를 저장한다.
- chunk별 bytes/rows, split/source 집계
- 제외 건수와 사유 저장

7. 종료 검증을 수행한다.
- 출력 row 수 일치 확인
- row 원자성 위반 없음 확인
- schema 일치 확인

8. 완료 로그를 출력한다.

## 5) 파일 1개 처리 스도코드
`파일_처리_030(file_path, split)` 절차:

1. JSON을 읽고 파싱한다.
2. 최상위 필수 키를 검사한다.
- `named_entity`가 없거나 배열이 아니면 파일 단위 오류로 집계하고 파일 스킵
3. `named_entity` 배열을 인덱스 순서대로 순회한다.
4. 각 기사 레코드에 대해 `기사_정규화(record, split, file_path, idx)` 호출
5. 반환된 row를 상위 스트림으로 전달한다.

---

## 6) 기사 정규화 스도코드
`기사_정규화(record, split, file_path, idx)` 절차:

1. 입력 키를 읽는다.
- `content_items = record.content` (배열 기대)
- `title_items = record.title` (배열 기대)

2. 본문 텍스트를 만든다.
- `본문_문장목록 = content_items[*].sentence`를 순서대로 수집
- 각 문장에 `문장_정규화()` 적용(좌우 공백 제거, 내부 연속 공백 1칸 치환)
- 빈 문자열 문장은 제거
- 남은 모든 문장을 `BODY_JOINER`로 concat하여 `user_text` 생성

3. 제목 텍스트를 만든다.
- `제목_문장목록 = title_items[*].sentence`를 순서대로 수집
- 각 문장에 `문장_정규화()` 적용
- 빈 문자열 문장은 제거
- 남은 전체 문장을 `TITLE_JOINER`로 concat하여 `assistant_text` 생성

3-1. 장문 유지 규칙을 적용한다.
- `LONG_ARTICLE_POLICY`에 따라 `user_text`, `assistant_text`를 전처리 단계에서 자르거나 분할하지 않는다.
- 길이 제어(최대 토큰/잘라내기)는 학습 로더 단계에서만 수행한다.

4. 이상치 여부를 판정한다.
- 조건 A: `content_items`가 배열이 아니거나 비어 있음
- 조건 B: `title_items`가 배열이 아니거나 비어 있음
- 조건 C: `user_text` 길이 0
- 조건 D: `assistant_text` 길이 0
- 조건 E: 문자열 타입이 아닌 `sentence`가 포함됨(숫자/객체 등)
- A~E 중 하나라도 참이면 해당 기사 row를 제외하고 품질 로그에 사유 기록

5. row를 생성한다(이상치가 아닐 때만).
- `data_type = "FT"`
- `source = SOURCE`
- `split = split`
- `content = null`
- `messages = [`
  - `{role: "system", content: SYSTEM_PROMPT}`,
  - `{role: "user", content: user_text}`,
  - `{role: "assistant", content: assistant_text}`
  - `]`
- `token_count = 토큰수_계산(SYSTEM_PROMPT, user_text, assistant_text)`

6. 생성 row를 반환한다.

---

## 7) 문자열 정규화 유틸 스도코드
`문장_정규화(text)` 절차:

1. 입력이 문자열이 아니면 타입 오류 플래그를 반환한다.
2. 유니코드 정규화(NFC)를 적용한다.
3. `trim()`으로 좌우 공백을 제거한다.
4. 줄바꿈/탭 포함 연속 공백을 단일 공백으로 치환한다.
5. 정규화 결과 문자열을 반환한다.

`문장목록_concat(items, joiner)` 절차:

1. 빈 리스트 `정규화_문장들`을 준비한다.
2. items를 순회하면서 `sentence`를 꺼내 `문장_정규화()` 적용한다.
3. 타입 오류는 카운트만 올리고 제외한다.
4. 빈 문자열이 아닌 문장만 `정규화_문장들`에 추가한다.
5. `joiner`로 결합해 최종 문자열을 반환한다.

---

## 8) token_count 계산 스도코드
`토큰수_계산(system_text, user_text, assistant_text)` 절차:

1. 세 텍스트를 순서대로 이어 붙인다.
2. `TOKENIZER_JSON`에서 로드한 토크나이저로 토큰화한다.
3. 토큰 개수를 int32로 반환한다.
4. 길이가 int32 범위를 넘으면 오류 처리한다.

주의:
- 데이터셋별로 다른 계산 로직/토크나이저를 쓰지 않는다.
- 특수 토큰(`<|bos|>`, `<|system|>` 등)은 전처리 단계에서 삽입하지 않는다.

---

## 9) Lance chunk 적재 스도코드
`청크_적재(row_stream)` 절차:

1. 현재 chunk id를 준비한다.
2. 빈 chunk 버퍼를 연다.
3. row를 1개씩 읽어 Arrow batch 또는 단일 row로 추가한다.
4. 추가 후 chunk 크기를 갱신한다.
5. 크기 판단:
- 아직 `CHUNK_TARGET_BYTES` 미만이면 계속 추가
- 초과했으면 “현재 row 포함 상태”로 chunk를 마감
- 다음 row부터 새 chunk 시작
6. 모든 row를 처리하면 마지막 chunk를 마감한다.
7. chunk 메타(`chunk_id`, `path`, `rows`, `bytes`)를 반환한다.

---

## 10) 품질 리포트/매니페스트 스도코드
`리포트_작성_030(run_id, 집계값)` 절차:

1. quality report 작성
- 파일 총계, 기사 총계, 생성 row 총계
- 제외 row 총계
- 제외 사유별 건수(A~E)
- 제외 샘플(사유별 최대 20건): `file_path`, `record_index`, `reason`
- 샘플 규칙: `QUALITY_SAMPLE_PER_REASON=20`은 "전체 제외를 20건만 남긴다"는 뜻이 아니라, 제외 사유별 상세 예시 목록을 최대 20건으로 제한한다는 의미다.
- 즉 집계 수치(제외 총계/사유별 건수)는 항상 전체를 기록하고, 샘플 목록만 상한 20건으로 절단한다.

2. manifest 작성
- `schema_version`, `token_count_version`
- run_id, 실행 시각
- source/split 집계
- chunk 목록(경로, bytes, rows)
- 전체 row 수

3. 파일 저장 경로
- `data/korean_processed/_manifests/quality_report-<run_id>.json`
- `data/korean_processed/_manifests/manifest-<version>.json`

## 11) 완료 검증 체크리스트
실행 종료 전에 아래를 모두 확인한다.

1. 모든 출력 row가 공통 schema와 정확히 일치하는가
2. `split` 값이 `train|val`만 존재하는가
3. 030 row가 모두 FT 규칙(`content=null`, `messages!=null`)을 만족하는가
4. `messages` 길이가 항상 3이고 순서가 `system,user,assistant`인가
5. `messages[0].content`가 지정된 system 프롬프트와 정확히 일치하는가
6. `messages[1].content`가 `content[*].sentence` concat 규칙과 일치하는가
7. `messages[2].content`가 `title[*].sentence` concat 규칙과 일치하는가
8. chunk 합계 row 수가 전체 row 수와 일치하는가
9. 어떤 chunk에서도 행 분할이 발생하지 않았는가
10. quality report와 manifest 집계가 서로 일치하는가

## 12) 실패 처리 정책
1. 스키마 불일치: 즉시 중단, 오류 로그와 샘플 row 저장
2. 토크나이저 로드 실패(`TOKENIZER_JSON` 누락/손상): 즉시 중단
3. 토큰 계산 실패: 해당 row 오류 집계 후 임계치 초과 시 중단
4. 파일 파싱 실패: 파일 단위 오류 집계, 정책 임계치 초과 시 중단
5. `named_entity` 구조 오류: 파일 스킵 후 품질 리포트에 누적
6. chunk 저장 실패: 즉시 중단, 현재 run_id 상태를 실패로 표시

## 13) 030 전용 실행 메모
1. 030은 파일 1개에 기사 레코드가 다수 포함되므로, 진행률 단위를 `file`과 `record`로 분리해 로그를 남긴다.
2. 주제 디렉터리(예: `문화`, `사회`, `스포츠` 등)는 경로 필터에만 사용하고 row 스키마에는 추가하지 않는다.
3. 동일 파일 내 기사 순서는 원본 배열 순서를 보존한다.
4. 후속 데이터셋(023/045/046 등) 확장 시에도 token_count 및 chunk 규칙은 그대로 재사용한다.
