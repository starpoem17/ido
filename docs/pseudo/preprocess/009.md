# 009 전처리 스도코드 (자연어 상세 버전)

## 0) 목적
`docs/plans/preprocess.md`의 확정 지침을 그대로 따르며,  
`009.전문분야_기술과학_한국어 멀티세션 데이터`를 공통 스키마로 평탄화한 뒤  
`duckdb -> arrow -> lance` 순서로 통합 저장소(`data/korean_processed/`)에 적재한다.

---

## 1) 사용자 확인 질문(진행 중 확정 필요)
아래 항목은 구현 전에 사용자에게 반드시 확인한다.

1. `token_count` 계산용 공통 토크나이저를 구체 경로로 고정할지 여부  
2. `_indices` 생성 시점(009 처리 직후 vs 배치 후처리)  
    사용자요청확인: 모든 데이터(009뿐 아니라 data/korean_raw 안의 모든 데이터)가 lance 데이터셋 안에 들어간 후 _indices 생성
3. `manifest-<version>.json` 버전 정책(정수 증가 vs 날짜 기반)  
    사용자요청확인: 정수 증가 선호
4. `quality_report`에 제외 세션 전체 목록을 담을지, 샘플만 담을지
    사용자요청확인: 집계 수치 + 제외 사유별 샘플만 담는다

현재 스도코드는 다음 기본값으로 작성한다.
- 토크나이저: `공통 토크나이저`라는 추상 인터페이스 사용
- 인덱스: 후처리 단계에서 분리 생성
- 버전: 정수 증가(`v0001`, `v0002`, ...)
- 품질 리포트: 전체 목록 + 샘플 요약 병행

---

## 2) 고정 상수와 경로
1. 입력 루트
- `TRAIN_INPUT = data/korean_raw/009.../Training/02.라벨링데이터/*.json`
- `VAL_INPUT = data/korean_raw/009.../Validation/02.라벨링데이터/*.json`

2. 출력 루트
- `OUT_ROOT = data/korean_processed/`
- `OUT_CHUNKS = data/korean_processed/chunks/`
- `OUT_MANIFESTS = data/korean_processed/_manifests/`
- `OUT_INDICES = data/korean_processed/_indices/`

3. 샤딩
- `CHUNK_TARGET_BYTES = 1,073,741,824` (1GiB)
- 행 원자성 보장: row 중간 분할 금지

4. 고정 메타
- `SOURCE = "009.전문분야_기술과학_한국어 멀티세션 데이터"`
- `DATA_TYPE = "FT"`
- `SYSTEM_PROMPT = "너는 기술과학 전문 비서야. 사용자의 질문에 친절하고 과학적으로 대답해."`

5. split 매핑
- `Training -> "train"`
- `Validation -> "val"`

---

## 3) 공통 스키마 선언 절차
다음 순서로 단일 PyArrow schema를 선언한다.

1. 컬럼 순서를 고정한다.
- `data_type: string`
- `source: string`
- `split: string`
- `content: string (nullable)`
- `messages: list<struct<role:string, content:string>> (nullable)`
- `token_count: int32`

2. null 규칙을 고정한다.
- FT row에서 `content=null`, `messages!=null`
- PT row에서 `messages=null`, `content!=null`
- 009는 FT만 생성하므로 항상 `content=null`

3. 스키마 버전 메타를 로드한다.
- 이전 manifest가 있으면 `schema_version`, `token_count_version` 검증
- 버전 불일치 시 즉시 중단하고 사용자 확인 요청

---

## 4) 전체 실행 오케스트레이션
`전처리_009_실행()` 절차는 아래와 같다.

1. 실행 시작 로그를 기록한다.
- run_id, 시작 시각, 입력 경로, 정책 요약

2. 입력 파일 목록을 수집한다.
- train 파일 목록 정렬
- val 파일 목록 정렬
- 총 파일 수 기록

3. DuckDB 정규화 단계로 진입한다.
- 파일별 파싱 결과를 중간 row 스트림으로 생성
- 이상치 세션 제외 정책 적용
- 표준 컬럼 6개로 relation 생성

4. Arrow 변환 단계로 진입한다.
- relation -> Arrow Table/RecordBatch
- 공통 schema 강제 캐스팅
- 캐스팅 실패 row는 오류로 집계하고 실행 중단 여부 판단

5. Lance chunk 적재 단계로 진입한다.
- chunk 버퍼를 열고 row를 순차 추가
- 바이트 추정/실측을 갱신
- 임계값을 넘으면 “방금 추가한 row까지 포함”하고 chunk 마감
- 다음 row부터 새 chunk 시작

6. 매니페스트와 품질 리포트를 저장한다.
- chunk별 bytes/rows, split/source 집계
- 제외 세션 목록과 사유 저장

7. 종료 검증을 수행한다.
- 예상 row 수와 실제 row 수 일치 확인
- row 원자성 위반 없음 확인
- schema 일치 확인

8. 완료 로그를 출력한다.

---

## 5) 파일 1개 처리 스도코드
`파일_처리(file_path, split)`를 자연어 단계로 정의한다.

1. JSON을 읽고 파싱한다.
2. 최상위 필수 키 존재를 검사한다.
- `sessionInfo`가 없으면 파일 단위 오류로 기록
3. 세션 배열을 순회한다.
4. 각 세션에 대해 `세션_정규화(session, split)`를 호출한다.
5. 반환된 row들을 상위 스트림에 전달한다.

---

## 6) 세션 정규화 스도코드
`세션_정규화(session, split)`는 아래 규칙을 따른다.

1. `dialog`를 읽어 원래 순서를 유지한다.
2. 발화 텍스트를 정리한다.
- 좌우 공백 제거
- 빈 문자열이면 `빈 발화`로 표시

3. 이상치 세션 여부를 먼저 판정한다.
- 조건 A: 빈 발화가 하나라도 있음
- 조건 B: `assistant -> assistant` 연속 턴이 있음
- 조건 C: 전체 순회 종료 후 unpaired user가 남음
- A/B/C 중 하나라도 참이면 세션 전체 제외

4. 제외되지 않은 세션만 row 생성으로 이동한다.
- 순차 스캔하면서 `speaker1`을 user 후보로 저장
- `speaker2`를 만나면 직전 user와 짝지어 1 row 생성
- row 생성 후 user 후보를 비운다

5. row 구성 규칙을 적용한다.
- `data_type="FT"`
- `source=SOURCE`
- `split`은 입력 split
- `content=null`
- `messages`는 길이 3 고정
  - 1번: system = `SYSTEM_PROMPT`
  - 2번: user = user 발화
  - 3번: assistant = assistant 발화
- `token_count`는 `system+user+assistant` concat으로 계산

6. 생성 row를 반환한다.

---

## 7) token_count 계산 스도코드
`토큰수_계산(system_text, user_text, assistant_text)` 절차:

1. 세 텍스트를 순서대로 이어 붙인다.
2. 공통 토크나이저로 토큰화한다.
3. 토큰 개수를 int32로 반환한다.
4. 길이가 int32 범위를 넘으면 오류 처리한다.

주의:
- 데이터셋별로 다른 계산 로직을 쓰지 않는다.
- 추후 다른 데이터셋(010/011/019)에도 동일 함수 재사용을 전제로 한다.

---

## 8) Lance chunk 적재 스도코드
`청크_적재(row_stream)` 절차:

1. 현재 chunk id를 준비한다.
2. 빈 chunk 버퍼를 연다.
3. row를 1개씩 읽어 Arrow batch 또는 단일 row로 추가한다.
4. 추가 후 chunk 크기를 갱신한다.
5. 크기 판단:
- 아직 `CHUNK_TARGET_BYTES` 미만이면 계속 추가
- 초과했으면 “현재 row 포함 상태”로 chunk를 마감
- 다음 row부터 새 chunk 시작
6. 모든 row를 처리하면 마지막 chunk를 마감한다.
7. chunk 메타(`chunk_id`, `path`, `rows`, `bytes`)를 반환한다.

---

## 9) 품질 리포트/매니페스트 스도코드
`리포트_작성(run_id, 집계값)` 절차:

1. quality report 작성
- 제외 세션 총계
- 제외 사유별 건수(A/B/C)
- 제외 세션 식별자(`file_path`, `session_id`, `reason`)
- 샘플 예시 N건

2. manifest 작성
- `schema_version`, `token_count_version`
- run_id, 실행 시각
- source/split 집계
- chunk 목록(경로, bytes, rows)
- 전체 row 수

3. 파일 저장 경로
- `data/korean_processed/_manifests/quality_report-<run_id>.json`
- `data/korean_processed/_manifests/manifest-<version>.json`

---

## 10) 완료 검증 체크리스트
실행 종료 전에 아래를 모두 확인한다.

1. 모든 출력 row가 공통 schema와 정확히 일치하는가
2. `split` 값이 `train|val`만 존재하는가
3. 009 row가 모두 FT 규칙(`content=null`, `messages!=null`)을 만족하는가
4. `messages` 길이가 항상 3이고 순서가 `system,user,assistant`인가
5. chunk 합계 row 수가 전체 row 수와 일치하는가
6. 어떤 chunk에서도 행 분할이 발생하지 않았는가
7. quality report와 manifest 집계가 서로 일치하는가

---

## 11) 실패 처리 정책
1. 스키마 불일치: 즉시 중단, 오류 로그와 샘플 row 저장
2. 토큰 계산 실패: 해당 row 오류 집계 후 임계치 초과 시 중단
3. 파일 파싱 실패: 파일 단위 오류 집계, 정책 임계치 초과 시 중단
4. chunk 저장 실패: 즉시 중단, 현재 run_id 상태를 실패로 표시

---

## 12) 후속 확장 메모
이 스도코드는 009 전용이지만, 다음 항목은 공통 모듈로 재사용한다.

1. 공통 schema 선언 절차
2. token_count 단일 계산 함수
3. chunk 적재/마감 규칙
4. manifest/quality report 작성 절차

즉, 010/011/019 확장 시에는 “입력 Adapter + 이상치 규칙”만 데이터셋별로 분기하고,  
저장/검증/샤딩 핵심 로직은 동일하게 유지한다.
