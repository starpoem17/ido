# 141 전처리 의사코드

## 목적
이 문서는 `141.한국어 멀티세션 대화`를 `docs/personal/preprocess/141.md`의 예시 형태 그대로 Lance row로 만드는 절차를 자연어로 설명한다.
이 데이터셋에서 Lance에 저장되는 row는 `messages`와 `content`를 함께 가지며, `FT`와 `PT` 학습은 같은 row를 서로 다른 필드로 사용한다.

## 고정값
구현할 때는 아래 값을 그대로 사용한다.

1. `source`는 `"141.한국어 멀티세션 대화"`로 둔다.
2. base system 문장은 `"당신은 사용자의 대화 상대로서 친절하고 긍정적으로 반응합니다."`로 둔다.
3. train 입력은 `data/korean_raw/141.한국어 멀티세션 대화/01-1.정식개방데이터/Training/02.라벨링데이터/**/*.json`에서 찾는다.
4. val 입력은 `data/korean_raw/141.한국어 멀티세션 대화/01-1.정식개방데이터/Validation/02.라벨링데이터/**/*.json`에서 찾는다.
5. `split`은 경로 기준으로 `train`, `val`만 사용한다.
6. `speaker1`은 `user`, `speaker2`는 `assistant`로 매핑한다.
7. `content` 결합 구분자는 공백 하나(`" "`)로 둔다.

## 입력 파일 탐색 절차
구현할 때는 아래 순서를 따른다.

1. train glob으로 파일을 모두 찾는다.
2. 파일 경로를 정렬한다.
3. 각 파일에 `split="train"`을 붙인다.
4. val glob으로 파일을 모두 찾는다.
5. 파일 경로를 정렬한다.
6. 각 파일에 `split="val"`을 붙인다.
7. 두 목록을 합쳐 입력 파일 목록으로 사용한다.

## 파일 처리 절차
파일 하나를 처리할 때는 아래 순서를 따른다.

1. JSON 파일을 읽는다.
2. 파싱에 실패하면 파일 단위 품질 이벤트를 남기고 다음 파일로 넘어간다.
3. 최상위의 `sessionInfo`를 꺼낸다.
4. `sessionInfo`가 없거나 배열이 아니면 파일 단위 품질 이벤트를 남기고 다음 파일로 넘어간다.
5. 최상위의 `personaInfo.clInfo.personaFeatures`를 읽어 system 확장에 사용할 원본 배열로 보관한다.
6. `sessionInfo`의 각 원소를 세션 1개로 보고 순서대로 처리한다.

## 세션 정규화 절차
세션 하나를 row로 바꿀 때는 아래 순서를 따른다.

1. 세션에서 `sessionID`를 읽는다.
2. 세션에서 `dialog`를 읽는다.
3. `dialog`가 없거나 배열이 아니면 이 세션은 버리고 품질 이벤트를 남긴다.
4. `dialog`를 처음부터 끝까지 순회한다.
5. 각 turn에서 `speaker`와 `utterance`를 읽는다.
6. `utterance`가 문자열이 아니면 이 세션은 버리고 품질 이벤트를 남긴다.
7. `utterance`는 좌우 공백을 제거한 뒤 사용한다.
8. 좌우 공백 제거 후 빈 문자열이면 이 세션은 버리고 품질 이벤트를 남긴다.
9. `speaker`가 `speaker1`이면 role을 `user`로 바꾼다.
10. `speaker`가 `speaker2`이면 role을 `assistant`로 바꾼다.
11. 그 외 값이면 이 세션은 버리고 품질 이벤트를 남긴다.
12. 정규화된 turn을 `{role, content}` 형태로 임시 배열에 넣는다.
13. 모든 turn을 모은 뒤 배열이 비어 있으면 이 세션은 버린다.
14. 첫 role이 `user`가 아니면 이 세션은 버린다.
15. 두 turn 연속으로 같은 role이 나오면 이 세션은 버린다.
16. 마지막 role이 `user`이면 마지막 turn 하나만 제거하고 `fixup` 품질 이벤트를 남긴다.
17. 마지막 `user`를 제거한 뒤 turn이 비었거나 마지막 role이 `assistant`가 아니면 이 세션은 버린다.
18. 최종 turn 배열에 `assistant`가 하나도 없으면 이 세션은 버린다.

## system 문장 생성 절차
FT용 system 문장은 아래 규칙으로 만든다.

1. base system 문장으로 시작한다.
2. `personaInfo.clInfo.personaFeatures`가 배열이면 순서대로 순회한다.
3. 각 feature가 문자열이면 좌우 공백을 제거한다.
4. 좌우 공백 제거 후 빈 문자열이 아니면 유효 feature 목록에 넣는다.
5. 유효 feature가 하나 이상이면 system 문자열 뒤에 아래 블록을 덧붙인다.
6. 덧붙이는 형식은 `\n[clInfo persona]\n` + `유효 feature를 \n으로 join`이다.
7. 유효 feature가 없으면 base system 문장만 사용하고 `fixup` 품질 이벤트를 남긴다.

## row 생성 절차
정규화에 성공한 세션은 아래 형태의 row 하나를 만든다.

1. `data_type`은 `"dialog"`로 둔다.
2. `source`는 고정값을 넣는다.
3. `split`은 입력 파일에서 가져온 값을 넣는다.
4. `messages`는 새 배열로 만든다.
5. `messages[0]`에는 system 문장 생성 절차로 만든 문자열을 `role="system"`으로 넣는다.
6. 그 뒤에는 정규화된 turn을 순서대로 그대로 넣는다.
7. `content`는 `messages`에서 system을 제외한 user/assistant의 `content`를 원순서대로 공백 하나로 이어 붙인 문자열로 둔다.
8. `token_count`는 저장 직전에 FT 직렬화 기준으로 계산한다.

## PT 사용 전략
이 데이터셋의 PT 입력은 별도 PT row를 만들지 않고 같은 row의 `content`를 사용한다.

1. PT 학습 시 row의 `content`를 그대로 사용한다.
2. `messages`는 PT 입력 생성에서 사용하지 않는다.

## FT 직렬화와 token_count
`token_count`를 계산할 때는 아래 순서를 따른다.

1. `messages`를 `<|system|>...<|user|>...<|assistant|>...` 형태로 직렬화한다.
2. 직렬화된 문자열을 공통 토크나이저로 인코딩한다.
3. 나온 토큰 수를 `token_count`에 넣는다.

## 품질 이벤트 기록 방식
품질 이벤트를 남길 때는 최소한 아래 정보를 기록한다.

1. dataset은 `141`
2. split
3. file path
4. session id
5. reason code
6. reason detail
7. sample text 일부
8. `skip`, `fixup`, `error` 중 성격

## 구현 체크리스트
1. 최종 row의 `data_type`이 항상 `dialog`인가
2. 최종 row의 `messages`가 `[system, user, assistant, ...]` 순서를 가지는가
3. `content`가 system 제외 user/assistant concat 규칙으로 생성되는가
4. system 문장에 `clInfo persona` 블록이 규칙대로 추가되는가
5. 빈 feature/누락 feature는 base system으로만 처리하고 이벤트를 남기는가
6. `token_count`를 FT 직렬화 기준으로 계산하는가
